# План: перенос рендера DotEngine на GPU

Цель: **60 FPS на любой настройке сетки**. Сейчас рендер полностью софтверный
(CPU), и на устройстве это упирается в два независимых потолка (замер из
debug-HUD: `ray 80ms`, `blit 32ms`, grid 110x55, 8 ядер → ~9 FPS):

1. **Рейкаст** — один луч на символ-ячейку по heightfield-миру. Даже с DDA и
   распараллеливанием по ядрам это остаётся тяжёлым при росте сетки.
2. **Вывод (blit)** — `AsciiView` делает до `gridW*gridH` вызовов
   `Canvas.drawBitmap` за кадр в один поток. ~32ms сами по себе = потолок ~30 FPS,
   и распараллелить Canvas нельзя.

GPU снимает **оба** потолка сразу: рейкаст становится fragment-шейдером
(параллелится на сотнях ALU), а вывод символов — одним инстансным draw-call'ом.

---

## Итоговая архитектура (GLES 3.0)

Референс по стеку: в аккаунте уже есть `jopaengune` (Android, OpenGL ES 3.0 /
JNI / C++) — оттуда можно переиспользовать инициализацию контекста и загрузку
шейдеров.

Кадр состоит из двух проходов:

### Проход A — рейкаст в low-res буфер символов (fragment shader)
- Рендерим один полноэкранный треугольник в offscreen-таргет размером **ровно
  `gridW x gridH`** (одна текстель = одна символ-ячейка).
- Fragment-шейдер для своей ячейки строит луч из камеры (uniforms: позиция,
  базис из yaw/pitch, FOV) и **рейкастит heightfield прямо в шейдере** тем же
  DDA-обходом по колонкам, что мы сделали на CPU (`Renderer` после PR #4).
- Мир процедурный и детерминированный (`World.heightAt`, value-noise, seed 1337)
  — переносится в GLSL один-в-один, ничего грузить в память не надо.
- Выход прохода A на ячейку: **luminance** (→ индекс глифа по рампе `Palette`) и
  **цвет** (тинт). Пакуем в один RGBA-текстель (напр. RGB=цвет, A=luminance).

### Проход B — вывод глифов (instanced draw)
- Атлас глифов (тот же набор символов, что у `Palette`/`AsciiView`) заливаем один
  раз как текстуру.
- Один **инстансный** draw-call на `gridW*gridH` квадов: вершинный шейдер по
  `gl_InstanceID` находит ячейку, читает её текстель из буфера прохода A, по
  luminance выбирает субрегион атласа (глиф), фрагмент тинтит его цветом ячейки.
- Итого весь вывод = **1 draw-call** вместо тысяч `drawBitmap`.

Оба прохода — на GPU, CPU в кадре почти ничего не делает (только обновляет
uniform'ы камеры). Стоимость слабо зависит от размера сетки → **60 FPS на любой
настройке** становится достижимым.

---

## Что переиспользуем из существующего кода (CPU)
- `World.heightAt` / value-noise / seed → портируем в GLSL (проход A).
- DDA-обход колонок из `Renderer` (PR #4) → это и есть тело рейкаст-шейдера.
- Рампа `Palette` (luminance→глиф) → определяет разбиение атласа в проходе B.
- Набор символов и метрики глифов из `AsciiView` → генерация атласа-текстуры.
- `Camera`/`Controls`/`Physics` остаются на CPU без изменений — они лишь дают
  uniform'ы (позиция/ориентация) в шейдер.
- `.obj`-объекты (`ObjLoader` + растеризация с depth) — **вне** первого этапа GPU
  (см. этапы ниже); сначала только terrain.

## Что меняется в архитектуре
- Рендер-таргет: `SurfaceView` + software `Bitmap` → **`GLSurfaceView`** (или свой
  EGL на `SurfaceView`).
- `Renderer.beginFrame/raymarch*` и `AsciiView.blit` → заменяются двумя GL-проходами.
- Софтверный путь **оставляем как fallback-флаг** (`Settings`), чтобы можно было
  сравнивать картинку/FPS и откатиться, если на каком-то устройстве GL себя ведёт
  плохо.

## Порядок работ (инкрементально, каждый шаг проверяем на устройстве)

1. **GL-каркас.** Завести `GLSurfaceView` + пустой рендер-цикл, вывести тестовый
   градиент. Убедиться, что EGL/контекст живут (переиспочать подход `jopaengune`).
2. **Атлас глифов.** Сгенерировать текстуру-атлас из набора символов `AsciiView`.
3. **Проход B на фиктивных данных.** Инстансный рендер сетки квадов, читающий
   случайный/тестовый буфер ячеек. Здесь проверяем, что «символьная картинка»
   рисуется одним draw-call и совпадает по виду с софтверной.
4. **Проход A — terrain-рейкаст в шейдере.** Портировать `heightAt`+DDA в GLSL,
   писать luminance+цвет в offscreen-текстуру; связать с проходом B.
5. **Камера/управление.** Прокинуть uniform'ы из `Camera`; сверить, что
   картинка и повороты совпадают с софтверным рендером (у нас уже был баг с
   зеркалом — свериться с базисом камеры особенно внимательно).
6. **HUD/тайминг.** Добавить GPU-таймеры (или хотя бы общий frame time) в тот же
   debug-HUD, чтобы мерить, а не гадать.
7. **`.obj`-объекты на GPU** (второй этап): рендер треугольников обычным
   растеризатором GL с depth-буфером *после* terrain-прохода, в те же ячейки.
8. **Fallback-флаг** и чистка: переключатель GL/software в `Settings`.

## Риски и заметки
- **Точность vs софт-рендер.** Пиксель-в-пиксель совпадения с CPU не будет
  (другая арифметика/порядок); цель — визуально идентичный terrain. Свериться
  особенно на краях блоков и на горизонте.
- **Совместимость GLES.** Держаться GLES 3.0 (широкая поддержка). Integer texture
  и `texelFetch` для буфера ячеек есть в 3.0.
- **Нельзя протестировать без железа.** Каждый этап требует сборки APK и запуска
  на устройстве — двигаемся маленькими шагами и сверяем HUD.
- **CI.** `android-build.yml` собирает APK при пуше в `main` / `workflow_dispatch`;
  на этой ветке автосборки по push не будет — проверять через `workflow_dispatch`
  или после мержа.
